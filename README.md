# Отчёт по email-рассылкам Capitalist и CardsPro

Дашборд по сценариям Sendsay: воронка по каждому письму цепочки, динамика по неделям, алерты и сравнение Capitalist / CardsPro × ru / en.

Каждый день в 06:47 МСК GitHub Actions забирает статистику из Sendsay API, сохраняет её в `data/daily.json` (коммитом — так в истории git видно, как менялись цифры) и публикует страницу на GitHub Pages.

В репозиторий попадают только агрегаты по письмам: сколько отправлено, доставлено, открыто, кликнуто, отписалось. Адресов и других персональных данных нет.

## Первый запуск

1. **Settings → Secrets and variables → Actions → New repository secret**
   - `SENDSAY_LOGIN` — логин аккаунта Sendsay
   - `SENDSAY_APIKEY` — API-ключ (Sendsay → Настройки → API-ключи). Ключу достаточно прав на чтение статистики.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
3. **Actions → «Обновить отчёт» → Run workflow**.

Через пару минут отчёт будет по адресу `https://mtarlykova-dev.github.io/email/`.

## Как поменять сценарии

Файл `config.json`:

```json
"scenarios": {
  "5": { "name": "Welcome Capitalist", "product": "Capitalist", "lang": "auto" }
}
```

Сейчас в отчёте: Регистрация Capitalist (1), Welcome CardsPro (3), Welcome Capitalist (5, вместе со старой EN-цепочкой 4), After KYB Capitalist (6), Реактивация CardsPro (8).

- ключ — ID сценария в Sendsay, номер из адреса `app.sendsay.ru/automation/workflows/<ID>` (число в конце имени выгрузки `stat_uni_…_41276.csv` — это не ID сценария);
- `product` — `Capitalist` или `CardsPro`, по нему работает фильтр и сравнение;
- `lang` — `ru`, `en` или `auto` (язык определяется по теме письма: кириллица → ru).

Сценарии, которых нет в конфиге, всё равно появятся в отчёте как «Сценарий #ID», пока `auto_discover: true`. Чтобы убрать сценарий, добавьте его ID в `exclude_scenarios`.

Если цепочку перенесли в новый сценарий (как Welcome Capitalist (en) → Welcome Capitalist (ru+en) 01.10), не исключайте старый, а склейте его с новым — так история писем сохранится в одних карточках и графиках:

```json
"4": { "name": "Welcome Capitalist (en), до объединения 01.10", "merge_into": "5" }
```

В `data/daily.json` строки остаются с исходным ID, склейка делается только при сборке страницы.

Порядок писем в цепочке — в `letters` у сценария: по каждому языку список фрагментов темы или названия письма по порядку. Так письмо остаётся на своём месте, даже если его переименовали в Sendsay:

```json
"5": { "name": "Welcome Capitalist", "letters": {
  "ru": ["Добро пожаловать в Capitalist", "Агентство, команда или фрилансер", "Тарифы и карты"],
  "en": ["Welcome to Capitalist", "Agency, team, or freelancer", "Fees without surprises"] } }
```

Если `letters` не задан, номер берётся из начала названия («1. …», «(2) …»), а если его нет — по дате первой отправки (в отчёте такое письмо помечено «порядок не задан»). При добавлении нового письма в цепочку допишите его в `letters`.

Как читать карточку письма:

- у CTR и CTOR справа — изменение к прошлому периоду такой же длины (для «Всё время» не показывается);
- у отписок и ошибок — «в норме» или «выше порога»; порог тот же, что у алертов (`unsub_rate_max`, `bounce_rate_max`), но считается за выбранный период, а алерты — за последние `rate_window_days` дней;
- если у письма за период доставлено меньше `display.min_delivered` (50), сравнения не показываются, цифры серые;
- внешние ориентиры (блок `benchmarks`, GetResponse, данные 2023) — серой строкой под карточкой и в таблице внизу страницы. OR не сравнивается: открытия завышены из-за Apple Mail Privacy Protection.

Пороги алертов — в блоке `alerts`:

| Параметр | Что значит |
|---|---|
| `silence_days` | Срочный алерт, если сценарий не отправлял письма столько полных дней подряд, хотя за 4 недели до последней отправки отправлял. В алерте — реальный срок тишины и дата последней отправки |
| `volume_drop_ratio` | Объём за неделю упал ниже этой доли от обычного |
| `bounce_rate_max` | Ошибки доставки письма за `rate_window_days` выше порога (3%: ориентир для триггерных писем 2,4%, для welcome 4%). Один алерт на сценарий со списком писем |
| `unsub_rate_max` | Отписки письма за `rate_window_days` выше порога (0,6%: ориентир для триггерных писем 0,38%, для welcome 0,94%). Один алерт на сценарий со списком писем |
| `rate_window_days`, `min_events` | Окно для ошибок и отписок (14 дней) и минимум событий (3), чтобы одна отписка на малом объёме не давала алерт |
| `or_drop_ratio` | OR письма за 2 недели упал ниже этой доли от OR за 8 недель до этого |

## Загрузить данные вручную

Если API недоступен или нужна история до `start_date`: выгрузите «Экспорт» из сценария в Sendsay и загрузите zip/csv через GitHub (Add file → Upload files) в папку с ID сценария, например `imports/5/` для Welcome Capitalist. Workflow сам разберёт файл, добавит данные и переложит его в `imports/done/5/`.

После первого запуска в сводке workflow (Actions → запуск → Summary) есть таблица «Сценарии из Sendsay API»: какие ID пришли и какие письма в них. Если ID в API не совпали с номерами из адресов, поправьте ключи в `config.json` по этой таблице.

## Пароль

Отчёт закрыт паролем. При сборке данные шифруются (PBKDF2-SHA256 → AES-256-GCM) паролем из секрета `REPORT_PASSWORD`, страница расшифровывает их в браузере. Открытый `report.json` на сайт не публикуется; если секрета нет, сайт публикуется без данных.

Цифры отчёта (`data/daily.json`, `data/alerts.json`) в репозиторий больше не сохраняются: каждый запуск собирает их заново из Sendsay с `start_date`. Сменить пароль: обновить секрет `REPORT_PASSWORD` и перезапустить workflow.

## Конверсии в целевые действия

Блок на странице отчёта: у каждой цепочки своё целевое действие, а выгрузка из бэк-офиса сопоставляется с открытиями и кликами по письмам.

| Цепочка | Целевое действие | Окно |
|---|---|---|
| Регистрация Capitalist (вход и 7 дней простоя) | любое действие в ЛК: пополнение, транзакция, верификация KYC или KYB | 7 дней |
| Welcome Capitalist | пройдена верификация KYC или KYB (дополнительно — пополнение) | 7 дней |
| After KYB Capitalist | первое пополнение баланса или транзакция | 7 дней |
| Welcome CardsPro | выпуск первой карты (дополнительно — пополнение карты) | 7 дней |
| Реактивация CardsPro | первая операция после входа в цепочку | 14 дней |

Цели и окна меняются в `config.json` → `conversions.goals`.

**Как считается.** Для каждого получателя цепочки берётся первое целевое действие после первого письма цепочки. Если до него в пределах окна был клик по письму этой цепочки — действие засчитывается последнему такому письму («после клика»); если клика не было, но было открытие — «после открытия»; иначе — «сами». Клики в Telegram считаются так же, как на сайт: Sendsay записывает клик до перехода, а само действие приходит из бэк-офиса. Отдельно отчёт показывает, кто сделал целевое действие ещё до первого письма и кто продолжал получать письма после него (проверка условий входа и выхода в сценариях).

**Откуда данные.**

- `scripts/fetch_touches.py` каждый день забирает из Sendsay, кто получил, открыл и кликнул какое письмо сценария за последние `conversions.days` дней (90). Полные адреса ссылок не сохраняются — только тип перехода: сайт/ЛК, Telegram, другое.
- `data/touch.json` с адресами живёт только в раннере GitHub Actions и в `.gitignore`. В отчёт `build.py` кладёт вместо email, логина и ID хэши (HMAC-SHA256, ключ из пароля отчёта) — и только внутри зашифрованных данных.
- Выгрузка бэк-офиса загружается на странице отчёта и обрабатывается **только в браузере**: страница хэширует email, логин и ID из файла тем же способом и сравнивает хэши. Файл никуда не отправляется и в репозиторий не попадает. Итоги и строки для проверки можно скачать в CSV.

**Шаблон выгрузки** — `site/templates/backoffice_events_template.csv` (на странице — кнопка «Скачать шаблон»), инструкция для выгрузки — `docs/backoffice_export.md`.

Не кладите выгрузку бэк-офиса в репозиторий: он публичный.

Проверить блок на выдуманных данных:

```
python scripts/demo_data.py
python scripts/build.py --data data/demo.json --touch data/touch_demo.json
python -m http.server -d _site 8000
```

и загрузить на странице `data/demo_backoffice.csv`.

## Массовые рассылки

Отдельная вкладка отчёта (`…/email/#mass`): все выпуски Sendsay, отправленные **не из сценария**. Их забирает `scripts/fetch_campaigns.py` — одна строка на выпуск, открытия и клики за всё время (они копятся несколько дней после отправки, поэтому период перезапрашивается целиком при каждом обновлении). Данные лежат в `data/campaigns.json`, в репозиторий не коммитятся и на сайт попадают только зашифрованными.

На вкладке: KPI за период с изменением к прошлому периоду, график «столбец на рассылку» по выбранной метрике, таблица всех рассылок с сортировкой и сравнение «массовые / триггерные / ориентир по финансовым услугам». Фильтры продукта, языка и периода общие с триггерной вкладкой.

Настройки — блок `campaigns` в `config.json`:

- `start_date` — с какой даты брать выпуски (пусто — общий `start_date`);
- `min_sent` — выпуски с меньшим числом получателей (тесты, отправки на себя) скрываются, на странице видно, сколько скрыто;
- `products` — продукт по фрагменту названия или темы выпуска (`"CardsPro": ["cardspro", …]`), иначе `default_product`;
- `thresholds` — когда отписки и ошибки в таблице подсвечиваются красным.

**Рассылки из других сервисов** (например, amo) добавляются вручную через секрет `MANUAL_CAMPAIGNS` — JSON-список, по объекту на рассылку:

```json
[{"source": "amo", "dt": "2026-10-29 15:55", "subject": "Тема письма", "product": "Capitalist",
  "sent": 20, "delivered": 20, "u_opens": 4, "u_clicks": 2, "unsubs": 0}]
```

Время — по Москве. В таблице такие рассылки подписаны «amo · внесено вручную». Цифры в репозиторий не попадают; чтобы добавить новую, обновите секрет целиком (Settings → Secrets and variables → Actions) и перезапустите «Обновить отчёт».

Язык рассылки определяется по теме (кириллица → ru). Если шаг загрузки упадёт, триггерная часть отчёта всё равно обновится.

Локальная проверка: `python scripts/demo_data.py && python scripts/build.py --data data/demo.json --touch data/touch_demo.json --campaigns data/campaigns_demo.json`.

## Цепочка → воронка amoCRM (вкладки CRP и CAP)

Вкладка `…/email/#crp`. Конверсия: человек из цепочки Welcome CardsPro (сценарий 3) перешёл по ссылке из любого письма **на сайт или в ЛК** (домены Capitalist/CardsPro; Telegram и соцсети не считаются), и в течение 30 дней после этого его сделка в воронке CRP перешла на этап **1st payment**, **Integration process** или **Successfully**. Каждый человек считается один раз — по первой такой смене этапа; конверсия засчитывается письму, из которого был последний переход до неё. Для сравнения показано, сколько получателей без перехода на сайт дошли до этих этапов за 30 дней от первого письма.

Данные:
- клики по людям — `scripts/fetch_touches.py` (Sendsay), тип ссылки определяет `dest_of`; в логе шага видно, какие домены куда отнесены;
- смены этапов — `scripts/fetch_amo.py`: события `lead_status_changed` в воронке `amo.pipeline_id` на этапы из `cardspro_crm.statuses` и email контактов этих сделок.

Оба файла (`data/touch.json`, `data/amo.json`) содержат адреса, поэтому в репозиторий не попадают; в отчёт идут только агрегаты.

Нужен секрет **`AMO_TOKEN`** — долгосрочный токен закрытой интеграции amoCRM (amo → amoМаркет → ⋯ → Создать интеграцию → закрытая, права на чтение сделок и контактов → вкладка «Ключи и доступы» → «Сгенерировать токен»). Настройки — блоки `amo` и `cardspro_crm` в `config.json`: окно (`window_days`), этапы (ID → название), какие клики считать (`click_dest`).

Вкладок две, обе настраиваются в `config.json → crm_tabs` (ключ — адрес вкладки):

- `crp` — Welcome CardsPro (сценарий 3) → воронка CRP: 1st payment, Integration process, Successfully;
- `cap` — Welcome Capitalist (сценарий 5, вместе со старой EN-цепочкой 4) → воронка CAP: Verification, Integration process, 1st payment, Successfully.

Правило одно для обеих: переход из любого письма на сайт или ЛК, затем в течение 30 дней сделка переходит на любой из этапов. Новая вкладка такого вида — новый блок в `crm_tabs` и кнопка в `site/index.html` (массив `CRM_TABS`).
